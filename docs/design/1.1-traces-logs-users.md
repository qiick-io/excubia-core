Status: **DRAFT, for discussion.** Written 2026-11-09, during the feature freeze before 1.0.0. Nothing here is built, and nothing here changes `docs/runtime-schema.json`, `excubia.schema.json`, `docs/CONTRACTS.md` or a snapshot. The schema fragments below are drafts and are not in any shipped schema.

| Core issue | excubia-app counterpart | Runtime type |
| --- | --- | --- |
| #243 sampled request traces | excubia-app#230 traces viewer | `trace` |
| #244 log entries, error and above | excubia-app#231 log entries viewer | `logEntry` |
| #245 pseudonymous user counts | excubia-app#232 affected users | `users` |
| (scope added 2026-11-09) personal data levels | permissions, encryption, audit, retention, erase/export | `privacy.level`, `x-excubia-personal` |

Milestone: v1.1.0 in both repositories. Sources read for this design: `docs/CONTRACTS.md`, `docs/VERSIONING.md`, `docs/runtime-schema.json`, `docs/SECURITY-MODEL.md`, `docs/guides/runtime-monitoring.md`, `docs/guides/privacy.md`, `src/Laravel/RuntimeCollectorService.php`, `src/Services/RuntimeBufferService.php`, `src/Laravel/ExcubiaPushRuntimeCommand.php`, and in excubia-app `app/Http/Requests/StorePushedRuntimeRequest.php`, `app/Actions/StorePushedRuntimeAction.php`, `docs/API.md` and `docs/compatibility.md` (all on `develop`).

## 1. Summary

- All three features go out through the existing `POST /api/runtime` push as **new runtime types**. They are off by default. There is no new endpoint, no new protocol version and no change to a frozen field.
- Traces and log entries get **their own local buffers and size caps**, so they can never push out the per-minute aggregates. User counts are tiny and go into the existing runtime buffer when the push runs.
- No batch may exceed **512 KB** of encoded JSON. That is half of excubia-app's default body limit (`EXCUBIA_PUSH_MAX_KILOBYTES`, 1024 KB). Larger buffers are split into several batches, each with a deterministic `batchId`.
- Privacy: the default level stays **aggregate**, which is everything Excubia does today. Traces and log entries reuse the masks Excubia already has (`maskSql`/`normaliseSql`, `ExceptionPayloadService::mask()`, `keyPrefix()`). By default, user counts leave the host as **counts only**, built from a fixed-size HyperLogLog register file on local disk. Hashes never go to disk or over the network.
- Two higher levels (**pseudonymous** and **identified**) are separate opt-ins, and both sides must agree. Every personal field is marked `x-excubia-personal` in the schema. Core sends such a field only when the app said, in its last push response, that the project accepts that level. The app stores those fields encrypted, behind a permission, audited, with shorter retention, and offers erase and export.
- Before 1.0.0, a few small things make 1.1 painless, mostly on the app side (tolerance tests, and an additive `capabilities` key in the success body). They are listed with their risk in §10. None of them changes a contract.

## 2. Compatibility

### 2.1 Why new runtime types on `/api/runtime`

| Option | Verdict |
| --- | --- |
| **New entries in `runtime.aggregates`, with new `type` values** (chosen) | `docs/CONTRACTS.md` already makes the app accept a batch that holds unknown types and skip only those entries. excubia-app 1.0 does this (`StorePushedRuntimeRequest`: an unknown type only needs a non-empty string `type`; `StorePushedRuntimeAction` skips it and increments `skipped_runtime_aggregates`, shown on Settings → System; the batch still answers `201`). The test `skips and counts entries of an unknown type` in `tests/Feature/Api/RuntimeContractTest.php` covers nested values (`'whatever' => ['nested' => true]`). The skip is visible to the operator, which is useful: "the app does not know `trace` yet, upgrade it". |
| New top-level key in `runtime` (`runtime.traces: [...]`) | Also accepted by app 1.0 ("unknown keys anywhere are accepted and ignored"), but it is dropped silently and never counted. It also adds a payload key that must be frozen in CONTRACTS. Rejected. |
| New endpoint (`/api/traces`) | App 1.0 answers `404`, which is a non-2xx. Core keeps the batch and stops that buffer until the cap drops it. Older apps would need special handling, and a new endpoint is a contract change on both sides. Rejected. |
| `protocolVersion` 2 | Only for breaking changes, with a new major of both (`docs/API.md`, versioning policy). Rejected. |

A trace or log entry is not an aggregate in the arithmetic sense. Each still carries `bucket`, `sampleRate`, `count` and `errorCount`, so it passes `RuntimeBufferService::isAggregate()`, holds the invariants every reader of `aggregates` relies on, and needs no special case in app 1.0's generic rules.

### 2.2 Core 1.1 → app 1.0

| What core 1.1 sends | What app 1.0 does | Result |
| --- | --- | --- |
| A runtime batch with known types plus `trace` / `logEntry` / `users` entries | Validates the known entries. The unknown ones need only `type`, are skipped on store, and are counted in `skipped_runtime_aggregates` | `201 {"status":"stored"}` (or `200` duplicate). Known data is stored, nothing is lost. |
| A batch that holds only `trace` entries (trace buffer) | Same; the batch id is recorded | `201`. Nothing is stored except the idempotency row. |
| Personal fields (§6) | Never sent: app 1.0 does not advertise a privacy level (§6.4), and core sends personal fields only to an app that advertises one | — |

Costs on an app 1.0: one or two extra requests a minute per server (trace and log buffers, §3.3), extra idempotency rows, and a skip counter that keeps growing. To avoid the wasted bandwidth, core 1.1 reads the app's `capabilities` (§6.4) when the app sends them. When `types` is present and does not list `trace`, core keeps the trace buffer but sends nothing from it, and prints once per run: `excubia-app does not store trace entries yet; upgrade the app (traces kept locally up to runtime.traces.bufferMaxBytes).` When `capabilities` is missing (app 1.0 without recommendation A2, §10), core sends anyway and app 1.0 skips the entries. That is safe, only wasteful.

### 2.3 Core 1.0 → app 1.1

Core 1.0 never sends the new types. App 1.1 must:

- keep every 1.0 type and shape valid, with no new required field on a known type;
- show the Traces / Logs / Users views empty, with the line "needs excubia-core 1.1 and `runtime.traces` / `runtime.logEntries` / `runtime.users`" (the same pattern as the "Needs excubia-core" column of `docs/compatibility.md`);
- answer with `capabilities` (§6.4), which core 1.0 ignores. Core 1.0 already decodes the success body as a JSON object and ignores unknown keys (`SymfonyHttpClientService::postJson`).

### 2.4 Core 1.1 → app 1.1

The app validates the new types with their own rules (drafts in §4). A value it does not know in an enumerated field, such as a span `kind` or a trace `reason`, only needs to be a string. The entry is stored, and the span is drawn as "other", exactly as #169 already handles enumerations. Unknown span kinds must never reject a batch.

### 2.5 Payload size and batch splitting

Facts on `develop` today:

- The app answers `413` above `EXCUBIA_PUSH_MAX_KILOBYTES` (default 1024 KB; PHP `post_max_size` caps it first, 16 MB in the Docker image).
- Core caps each buffer at `runtime.bufferMaxBytes` (default 1 MiB) of NDJSON. Lines are written with `JSON_UNESCAPED_SLASHES | JSON_UNESCAPED_UNICODE`.
- The push body is encoded by Symfony HttpClient's `json` option, which escapes `/` and non-ASCII characters. A batch close to the 1 MiB cap can therefore encode to more than 1024 KB. Merging usually shrinks a batch a lot, but a buffer full of distinct entries (many SQL shapes, deprecation messages) does not shrink.
- Any non-2xx stops that buffer for the run and keeps the batch (`ExcubiaPushRuntimeCommand::sendBuffer`). A `413` is therefore retried every minute until the cap trims the oldest lines enough. This is the documented ponytail ("a batch the app keeps rejecting with a 4xx stays until the cap drops it"). It heals itself by losing data, and it blocks newer batches until then.

Design for 1.1 (internal, no contract change):

1. **Chunk at claim time.** `claimBatches()` writes the claimed lines into batch files of at most `PUSH_CHUNK_BYTES` = 512 KB of NDJSON each, never splitting a line. Every chunk gets its own fresh v4 `batchId` in its file name, as today, so retries stay idempotent. With 2× headroom, escaping and the envelope cannot reach 1024 KB.
2. **One trace is at most 64 KB** (`MAX_TRACE_BYTES`, §4.1). A trace that would be larger is cut, spans first and then SQL shapes, and marked `isTruncated`. So a 512 KB chunk holds at least 8 traces (worst case) and about 30 to 60 typical ones.
3. **On a `413`, split and retry once.** Split the batch file in two halves. Each half gets a batch id derived from the parent: the first 16 bytes of `sha256(parentBatchId + ":" + half)`, with the v4 version and variant bits set, so it matches the app's `batchId` regex. Then retry. A single line that is still too large is dropped and counted in the command output. This removes the 4xx ponytail for size, the only 4xx with a mechanical fix.
4. **At most `runtime.maxBatchesPerRun` batches per buffer and run** (draft default 4), so a backlog after an outage is drained over several minutes instead of using up the app's rate limit (`EXCUBIA_PUSH_REQUESTS_PER_MINUTE`, 30 per project, shared by all endpoints and servers).

Recommendation C2 (§10) brings step 3, and optionally step 1, to 1.0.x for the existing buffers, because the edge already exists there.

### 2.6 Buffer budgets per type

`RuntimeBufferService` caps a directory as a whole and drops the oldest lines first. If traces shared `storage/excubia/runtime/`, a burst of slow requests would evict request, job and query aggregates, which is exactly what #243 forbids. The service is already generic: exception capture uses a second instance on its own directory, and the push command passes a read closure for each buffer (`$read` in `sendBuffer`). So the budgets come from **separate directories**, not from a per-type cap inside one file.

| Directory | Holds | Cap key | Draft default | Read strategy |
| --- | --- | --- | --- | --- |
| `storage/excubia/runtime/` | every aggregate type, plus `users` (appended at push time) | `runtime.bufferMaxBytes` | 1 MiB (unchanged) | `read()`, merged |
| `storage/excubia/exceptions/` | exception groups | `exceptions.bufferMaxBytes` | 1 MiB (unchanged) | `ExceptionPayloadService::merge` |
| `storage/excubia/traces/` (new) | `trace` entries | `runtime.traces.bufferMaxBytes` | 1 MiB | `readEntries()`, then keep the top `maxPerMinute` per minute (§4.1), **never merged** |
| `storage/excubia/logs/` (new) | `logEntry` entries | `runtime.logEntries.bufferMaxBytes` | 256 KiB | `read()`, merged by dimensions (identical masked messages add up) |
| `storage/excubia/users/` (new) | HyperLogLog register files, one per minute, guard and kind | none, fixed size (§5.3) | ≈ 1 KiB per file, files older than 60 minutes removed | finalised into `users` aggregates by `excubia:push-runtime` |

The file names and layout under `storage/excubia/` are internal (`docs/CONTRACTS.md`, "Internal"). Adding directories is not a contract change. A core 1.0 that reads a directory written by 1.1 after a downgrade simply ignores the new ones.

### 2.7 Configuration keys (draft, 1.1)

These keys are additive in `excubia.schema.json` 1.1. A core 1.0 rejects them as unknown keys, which is the current, documented behaviour: "Unknown keys stay a configuration error". The 1.1 guide says so in a "needs excubia-core 1.1" line.

```jsonc
{
  "runtime": {
    "maxBatchesPerRun": 4,                 // per buffer and run, §2.5
    "traces": {
      "enabled": false,
      "sampleRate": 1,                     // head sampling: share of requests/jobs/commands that record spans at all
      "thresholdMs": 1000,                 // keep a recorded trace when its root took at least this long…
      "keepFailed": true,                  // …or failed (5xx, failed job, non-zero exit, reported exception)
      "maxSpans": 200,                     // per trace, then isTruncated and droppedSpanCount
      "maxPerMinute": 30,                  // kept traces per server and UTC minute, slowest/failed first
      "kinds": ["request", "job", "command", "scheduledTask"],
      "bufferMaxBytes": 1048576
    },
    "logEntries": {
      "enabled": false,
      "sampleRate": 1,
      "minimumLevel": "error",             // error, critical, alert, emergency; nothing below error
      "maxPerMinute": 100,                 // distinct masked messages per process and minute, then counted under "[over limit]"
      "bufferMaxBytes": 262144
    },
    "users": {
      "enabled": false,
      "guards": null,                      // null = every guard that authenticates; or a list of guard names
      "sendSketch": false                  // §5.4: counts only by default
    }
  },
  "privacy": {
    "skipPackages": [],                    // unchanged
    "level": "aggregate",                  // aggregate | pseudonymous | identified, §6
    "ipAddress": "none",                   // identified only: none | truncated | full
    "headers": [],                         // identified only: allowlist of request header names, never Authorization/Cookie
    "exceptionPayload": false,             // identified only: masked request input on exception groups
    "payloadMaskKeys": ["password", "password_confirmation", "token", "secret", "card", "iban"]
  }
}
```

The masks reuse `exceptions.maskPatterns`, so there is one list of project masks, not a second one for logs (open question Q4). `runtime.users` has no `sampleRate`: sampling would bias distinct counts. Every entry carries `sampleRate: 1`.

## 3. Collection and flushing

### 3.1 Where it hooks in

All three features reuse listeners `RuntimeCollectorService` registers already, and only when their own switch is on:

- Trace root: `RequestHandled` (requests, timed from `REQUEST_TIME_FLOAT` as today), `JobProcessing` → `JobProcessed` / `JobFailed`, `CommandStarting` → `CommandFinished` (top-level only, same rules as `command`), `ScheduledTaskStarting` → `Finished` / `Failed`.
- Spans: `QueryExecuted`, `ResponseReceived` (outgoing HTTP; `ConnectionFailed` as an error span), the cache events, `JobQueued` (dispatched job), `MessageSending` / `MessageSent`, `NotificationSent` / `NotificationFailed`, `MessageLogged` (level only), and the exception capture `reportable()` callback (class and fingerprint) when `exceptions.enabled`.
- Log entries: the existing `MessageLogged` listener, with its `isRecordingLog` loop guard. The channel comes from the existing logging tap (#174).
- Users: `RequestHandled` / `JobProcessed` read `auth()->guard($name)->id()` from guards that have **already resolved** a user. Excubia never triggers an authentication itself; it calls `hasUser()` first.

### 3.2 Tail decision

Spans are recorded in memory while the root runs (head sampled by `sampleRate`, at most `maxSpans`). When the root ends:

1. it is kept if `durationMs ≥ thresholdMs`, or if it failed and `keepFailed` is on;
2. otherwise the spans are discarded, with no disk write;
3. a kept trace is encoded, cut to `MAX_TRACE_BYTES`, and appended to `traces/` as one NDJSON line.

`maxPerMinute` cannot be enforced in memory under PHP-FPM, because nothing survives between requests. It is enforced on read: per UTC minute, keep failed traces first, then the slowest, up to `maxPerMinute`, and drop the rest. The disk cost of over-keeping is bounded by `traces.bufferMaxBytes`. The kept selection, never all traces of a busy minute, is what goes over the network.

### 3.3 Requests per minute

With every opt-in on, a server sends up to 4 requests a minute (runtime, exceptions, traces, logs) instead of 2 today. At the app's default of 30 requests a minute per project, that leaves room for about 7 servers instead of 15. Options: pack the trace and log chunks into one runtime envelope per run when both fit in 512 KB (preferred, internal to core), and/or raise the app default (open question Q6).

## 5. Users: hashing and HyperLogLog

### 5.1 Why not "in memory for the minute"

#245 says hashes are "kept in memory only for the minute". Under PHP-FPM nothing in PHP memory survives a request. Each request runs in a fresh request scope even when the worker process is reused, so a per-minute distinct set cannot live in memory. Octane and queue workers could hold one, but the FPM case decides the design.

### 5.2 Hash

`hmac = HMAC-SHA256(key = HMAC-SHA256("excubia-users-v1", app.key), message = guard + "\0" + (string) $user->getAuthIdentifier())`

- The key is derived from `app.key` and never leaves the host. excubia-app never sees it, so it cannot compute the hash of a candidate user id: no membership test, no dictionary attack from the app side.
- The HyperLogLog uses only the first 64 bits: the top 10 bits give the register index, and the rank is the number of leading zeros of the remaining 54 bits plus one.
- At the pseudonymous level, `userHash` is the first 16 bytes (32 hex) of a second HMAC with the label `excubia-user-id-v1`. A different label means a leaked `userHash` reveals nothing about the HyperLogLog bits, and the reverse.
- Rotating `APP_KEY` changes every hash. Distinct counts across the rotation overcount once, and `userHash` values start a new series. This is documented, not avoided.

### 5.3 Local register file

Per UTC minute, guard and kind (`seen`, `affected`), one file `storage/excubia/users/<minute>-<guard-sha8>-<kind>.hll` of 1024 bytes, precision 10 (standard error about 3.3 %, exact through linear counting for small numbers). Updating it for one authenticated request means: open the file, take the `flock` (shared with the buffer's lock discipline), `fseek` to the register, read one byte, write it back only when the new rank is larger, and unlock. That is O(1), at most one 1-byte write, and the disk use is fixed: about 2 KB per guard per minute, files older than 60 minutes removed.

`excubia:push-runtime` finalises every closed minute (`< now`). It estimates `distinctUsers` and `affectedUsers`, reads `count` and `errorCount` from a 16-byte counter header in the same file, appends one `users` aggregate per server and guard to the runtime buffer (as `server` and `health` samples are appended today), and deletes the files. **No hash and no id is ever written to disk**, only registers, which hold the maximum rank per bucket.

### 5.4 Decision: counts only by default

**Recommendation: `runtime.users.sendSketch: false` by default.** By default the wire carries `distinctUsers` and `affectedUsers` per server, guard and minute, and nothing derived per user. The sketch is a separate opt-in. Hashed ids for drill-down are not part of the `users` type at all; they belong to the pseudonymous privacy level (§6), where they are marked as personal.

Why:

1. **Smallest data surface.** Counts are aggregate statistics, the same class of data Excubia sends today, and `docs/guides/privacy.md` and SECURITY-MODEL can say "user counts, never ids or hashes" without a footnote.
2. **A sketch is safe, but harder to explain.** Registers cannot be reversed, and without `app.key` the app cannot test membership. Still, a sketch is derived from personal data, and a reviewer has to understand HyperLogLog to agree it is not personal data. Off by default keeps the default posture obvious; teams that want exact merges switch it on.
3. **The cost of counts only is known and visible.** Without sketches the app cannot merge distinct counts across minutes or servers. "Users per day" is shown as a range: at least the largest per-minute count, at most the sum. excubia-app#232 labels it as such. The single-server, per-minute numbers are exact enough for alerts ("N users affected in the last minute").
4. **Size.** A sketch costs about 2.8 KB per entry in base64 (two registers), so about 4 MB per day per guard per server in the app. That is acceptable as an opt-in, but not something to impose on every project.

Not recommended: sending hashed ids in `users` for drill-down. The same need is met, consistently with the rest, by the pseudonymous level on traces (`userHash`), behind the two-sided opt-in and the app's personal-data controls.

### 5.5 Users affected per exception group

excubia-app#232 also wants users affected per exception group and per route. A HyperLogLog per fingerprint and minute has unbounded cardinality. Options for 1.1: (a) the app derives it from kept traces that carry `userHash` (pseudonymous level only); (b) an optional `fingerprint` dimension on `users`, capped at 20 fingerprints per minute, with 1 KB per file. Recommendation: (b) for the "N users affected" alert badge, capped, counts only. See open question Q3.

## 6. Personal data levels (scope addition 2026-11-09)

Luca wants to evaluate collecting, as an explicit opt-in, what Excubia skips today on purpose: request detail (URL, IP, headers, payload on exception) and the authenticated user per request or trace, because "who did what" helps debugging and spotting anomalies. This section designs it so that the default stays exactly as today, and the higher levels are additive and need consent on both sides.

### 6.1 Levels

| `privacy.level` | Adds | User | URL | IP | Headers | Payload |
| --- | --- | --- | --- | --- | --- | --- |
| `aggregate` (default; everything up to 1.1 without this section) | — | counts only (`users`) | route name only | never | never | never |
| `pseudonymous` | `userHash` on traces (and on exception groups, §6.3), `routeTemplate` | HMAC per guard (§5.2); no label | route template with placeholders, never values | never | never | never |
| `identified` | `user` {guard, id, label}, `path`, optionally `ipAddress`, `headers`, exception `request` payload | id, and a display label when the app registers a resolver | full path; query string as `?[query]` | `privacy.ipAddress`: `none` (default), `truncated` (IPv4 /24, IPv6 /48) or `full`, a separate opt-in | `privacy.headers` allowlist; `Authorization`, `Proxy-Authorization`, `Cookie`, `Set-Cookie` never | `privacy.exceptionPayload`: the request input on exception groups only, keys in `payloadMaskKeys` and the exception masks applied, at most 4 KB, files as name and size only |

What stays the same at every level:

- Log messages and exception messages always go through the masks. A level never unmasks free text: free text can hold anyone's data, not only the authenticated user's.
- SQL bindings, cache values, mail recipients and bodies, AI prompts, Reverb payloads, Cashier payloads, credentials and tokens are never collected.
- The cache, mail, notification, auth, Scout and Pennant aggregates never gain personal fields. Personal fields exist only on `trace` and on exception groups.

**Display label resolver (identified).** A label such as a display name makes "who did what" readable. Excubia never guesses one (no `name` or `email` attribute lookups). The app registers it explicitly, for example `Excubia::resolveUserLabelUsing(fn (Authenticatable $user): ?string => $user->name)`, called at most once per user per request, cut to 200 characters, with errors swallowed. That static method becomes public API (see Q9). Without a resolver, only the id is sent.

### 6.2 Schema annotation `x-excubia-personal`

Every personal field, in `runtime-schema.json` and `exception-schema.json`, carries `"x-excubia-personal": "pseudonymous"` or `"identified"`, the lowest level at which it may appear. Rules:

- Core strips every field whose level is above the **effective level** (§6.4) at send time. The buffer may hold more, which matters when the app has just lowered its level, but the wire never does.
- excubia-app reads the annotations from the vendored schema (`tests/Fixtures/core/runtime-schema.json`) to drive four things: which columns it encrypts at rest, which UI elements need the new permission, what the audit log records, and what the shorter retention and the erase and export features cover. A contract test fails when a schema field marked personal has no storage mapping in the app.
- The annotation is additive. JSON Schema ignores unknown `x-` keywords, and the schema hash changes in 1.1 with the new `$defs` anyway.

### 6.3 Where personal fields live

- `trace`: as drafted in §4.1.
- Exception groups (`docs/exception-schema.json`): optional `userHash` (pseudonymous), and `users` (identified, at most 10 `{guard, id, label}` per group per batch, to answer "who hit this") and `request` {`path`, `method`, `ipAddress`, `headers`, `input`}. One group merges many occurrences, so `request` is the most recent occurrence only. Exception groups are not de-duplicated by these fields, so they are not part of the fingerprint or the merge key.
- `logEntry` and `users`: no personal fields at any level.

### 6.4 Two-sided consent and capability negotiation

Core must never push more than the app accepts, and an app must never store more than the project allows.

1. **App side.** Each project has its own privacy level in the app (Settings → Privacy, default `aggregate`), set by a user with a new permission (`can-manage-personal-data`). Raising it records who did it and when in the audit log, and shows the legal notes of §6.6.
2. **The app advertises it** in every 2xx body of `/api/runtime` and `/api/exceptions`, as a new key. Additive keys in success bodies are allowed by the app's versioning policy:

   ```json
   {"status": "stored", "capabilities": {"privacyLevel": "aggregate", "types": ["request", "slowQuery", "…", "trace"], "skipped": 0}}
   ```

3. **Core caches it** in `storage/excubia/app-capabilities.json` (internal), keyed by the app URL's sha256, with a timestamp.
4. **Effective level** = the lower of `privacy.level` in `excubia.json` and the cached `privacyLevel`. When `capabilities` is missing (app 1.0), or the cache is older than 24 hours, or missing (first run), the effective level is `aggregate`. The first batches after the operator turns a level on in both places therefore go out without personal fields. That costs a minute of data and gains a safe default.
5. **App side, defence in depth.** App 1.1 drops every personal field above the project's current level before storing it, and counts the drops (Settings → System, `dropped_personal_fields`). It does not answer `422`: a level lowered in the app while core still holds an older cache must not wedge the buffer.
6. **App 1.0** never advertises a level, so core 1.1 never sends it personal fields. App 1.0 also ignores unknown keys in known types (`docs/API.md`, "Unknown fields and types"). Recommendation A1 (§10) adds a test before 1.0 that pins "unknown keys are never persisted", so even a core that strips wrongly cannot store personal data in a 1.0 app.

### 6.5 What the app must do at `pseudonymous` and `identified`

(excubia-app, new issues to open in v1.1.0 next to #230–#232.)

- **Encryption at rest** of every personal column (Laravel encrypted casts with the app's own key; key rotation through `APP_PREVIOUS_KEYS`). To allow lookups for erase and export, the subject is also stored as a keyed lookup hash computed with an app-side key: `HMAC(app key, guard + id)` for identified, `userHash` itself for pseudonymous.
- **Permission** `can-view-personal-data`, separate from viewing the project. Without it, the UI shows "personal data hidden", and the API and MCP tools return the same redaction.
- **Audit** of every view of a personal field: who, when, which project and which record. This means trace detail opens, user filters and exports, not list renders without personal columns. The audit log itself holds no personal values, only references.
- **Separate, shorter retention**: personal fields are nulled after `EXCUBIA_PERSONAL_RETENTION_DAYS` (draft default 7), while the non-personal remainder of a trace follows its own retention (48 h for traces, excubia-app#230).
- **Erase and export** per data subject (GDPR Art. 15, 17, 20): given a guard and an id (or a `userHash`), export every stored personal field as JSON, or erase it by nulling the fields and keeping the non-personal rows. Both are audited. Backups follow the backup rotation; the docs say so.
- **Level lowered**: personal fields above the new level are purged in a queued job, audited.

### 6.6 Legal position (summary, not legal advice)

- **Controller.** Excubia is self-hosted. The operator of the Laravel app and of excubia-app is the controller. qiick, as the author of open-source software, receives nothing and is neither controller nor processor. If the operator hosts excubia-app with a cloud provider, that provider is the operator's processor, as for the rest of their infrastructure.
- **Pseudonymous data is still personal data** (GDPR Recital 26): the operator holds `app.key` and can re-identify. Only the `aggregate` level, counts and sketches without the key, is outside the GDPR in practice, which is one more reason it is the default (§5.4).
- **Lawful basis.** Legitimate interest (Art. 6(1)(f)) for security, fraud and abuse detection and debugging is the usual basis. It needs a documented balancing test, and data minimisation is what makes it hold: levels, IP truncation, a header allowlist, payload only on exceptions, masks and short retention.
- **DPIA hint.** The identified level with full IPs and payloads, on a large user base, comes close to "systematic monitoring" (Art. 35). The app's Settings → Privacy page recommends a DPIA before raising the level, and links a short template in the docs. Art. 30 (records of processing), Art. 32 (security of processing, §6.7) and Art. 5(1)(e) (storage limitation, §6.5) apply. The user-facing privacy notice of the operator's app should mention error monitoring.
- **Defaults.** Art. 25 (data protection by default): everything off, `aggregate` by default, two-sided opt-in, and personal data never sent to an app that did not opt in.

### 6.7 Security impact

At `pseudonymous` and above, excubia-app becomes a store of personal data, and part of core's local buffer does too. Additions to make in `docs/SECURITY-MODEL.md` (core) and the app's `SECURITY-MODEL.md` in 1.1:

| Threat | Mitigation | Residual |
| --- | --- | --- |
| Theft of the excubia-app database or backups exposes users' activity | encryption at rest of personal columns, short retention, purge on level change | an attacker with the app key and the database reads everything |
| An insider browses users' activity | `can-view-personal-data`, audit of every view, erase and export audited | a permitted user can still read; the audit makes it visible |
| Over-collection through a header or payload field | header allowlist with hard-coded exclusions; `payloadMaskKeys` and the exception masks on payload values; 4 KB cap; no files | a field name no mask recognises; review `payloadMaskKeys` |
| Core sends personal data to an app or project that did not opt in | effective level = the lower of both sides, missing or stale capabilities count as `aggregate`, strip at send; the app drops fields above the level | a compromised app can advertise a higher level, but only to a core whose operator also set that level |
| Buffers on disk hold personal data | buffer lines with personal fields are encrypted with a key derived from `app.key` (libsodium `secretbox`, bundled with PHP, no new dependency), buffer caps unchanged, and personal fields stripped from batches older than the retention | the host's own storage protections still matter |
| A stolen project token | the token can only push, never read; a push cannot lower or raise the app's level | forged pushes as today |
| Re-identification from `userHash` | key never leaves the host; separate HMAC labels; keyed lookup hash on the app side | the operator can re-identify (by design: it is their data) |

Principles to amend: "Never users or IP addresses" becomes "Never users or IP addresses at the default `aggregate` level; the `pseudonymous` and `identified` levels need a matching opt-in in both `excubia.json` and the app".

## 7. Privacy model per type

| Type | Always sent (aggregate level) | Never sent at any level | Masking reused |

## 8. Overhead budgets and benchmarks

Today: the benchmark (`tests/Laravel/RuntimeOverheadBenchmarkTest.php`, `vendor/bin/pest --group=benchmark`) fails when the collector costs more than 1 ms per request with every type on. The guide quotes 0.15–0.5 ms. Draft budgets for 1.1:

| Path | Budget | Notes |
| --- | --- | --- |
| Traces off | 0 | no listener registered |
| One span recorded | ≤ 0.002 ms | array append plus `hrtime`; query shape memoised as in `duplicateQuery` |
| Request not kept (fast and successful), 100 spans | ≤ 0.25 ms | recording only; no encode, no disk |
| Kept trace: encode, cut and append | ≤ 0.5 ms | rare by design (slow or failed); one `flock` and one append |
| One log entry at error or above | ≤ 0.05 ms | 500-character message through the masks; cap of 20 entries per request |
| One authenticated request with users on | ≤ 0.03 ms | 2 HMACs, `flock`, a 1-byte read and at most a 1-byte write |
| Everything on (all 1.0 types plus 1.1 at their defaults), typical request | < 1 ms (the existing gate) | if this fails, the 1.1 defaults change, not the gate |

How to benchmark, in the same file and style as today: one `it()` per budget, a warm-up of 200 iterations, then the median of 5 runs of 2000 iterations, comparing types off with types on and printing both. The test fails only on the budget. Add a size test as well, not a timing one: build a worst-case trace (200 spans, 50 shapes of 2000 characters) and assert ≤ 64 KB, and a full trace buffer that chunks to batches ≤ 512 KB encoded with Symfony's flags. On the app side, excubia-app#230's load test pushes 512 KB trace batches at 4 requests a minute per server and records the validation and storage time per batch, plus the disk use per 1000 traces for the Sizing page.

## 11. Open questions for Luca

1. **Users sketch default.** Is counts only by default (§5.4) right, accepting that "users per day" is a range unless `sendSketch` is on? Or should the sketch be the default, since it is arguably not personal data?
2. **`capabilities` in app 1.0 (A2).** Land it before app 1.0.0? It is the only app change that makes core 1.1 cleaner with 1.0 apps.
3. **Users per exception group** (§5.5): an optional `fingerprint` dimension on `users` (capped at 20 per minute), or only through traces at the pseudonymous level?
4. **One mask list?** Should `logEntry` reuse `exceptions.maskPatterns` (proposed), or get `runtime.logEntries.maskPatterns`?
5. **`minimumLevel` below `error`?** #244 says error and above. Allow `warning` as an opt-in, or keep it fixed?
6. **Rate limit.** With traces and logs on, a server sends up to 4 requests a minute. Pack them into fewer envelopes in core (preferred), or raise the app's default `EXCUBIA_PUSH_REQUESTS_PER_MINUTE` from 30?
7. **Personal levels in 1.1 at all?** Approve §6 as the 1.1 scope, or ship traces, logs and users at the `aggregate` level in 1.1 and personal levels in 1.2 (they need the app's encryption, permission, audit and erase work first)?
8. **Route templates** (`users/{user}`) carry no values. Allow them at the `aggregate` level (more useful traces), or keep them at `pseudonymous`?
9. **Public API for the label resolver.** `Excubia::resolveUserLabelUsing()` would be the first public PHP API of the package (everything under `src/` is internal today). Is that acceptable, or should the label come from a config value (`privacy.userLabelAttribute`)?
10. **Personal retention default** in the app: 7 days?
11. **The core's own schema and unknown types.** `aggregates.items` in `runtime-schema.json` is a strict `oneOf`, so a third-party consumer validating 1.1 batches with the 1.0 schema rejects them, even though CONTRACTS tells apps to accept unknown types. Leave it (excubia-app does not validate with the schema), or relax it in 1.1 with a fallback branch?
