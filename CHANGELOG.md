# Changelog

All notable changes to **Excubia** (`qiick/excubia-core`) are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Changed

- `laravel-cors-wildcard` no longer warns on `*` without credentials, Laravel's stock CORS config (#139). It fails only for `*` with `supports_credentials`.

### Added

- Six more configuration posture checks (#130), run by `php artisan excubia:check` and `excubia:push` like the #73 ones and `skipped` ("requires Artisan", `not-applicable`) in `vendor/bin/excubia`: `laravel-app-key` (`app.key` empty, in any environment: fail, critical), `laravel-session-security` (in `production`, `session.secure` false while `app.url` is https, or `session.http_only` false: warn, medium, one row per key), `laravel-cors-wildcard` (in `production`, `cors.allowed_origins` contains `*` with `cors.supports_credentials`: fail, high; `*` alone: warn, low), `laravel-production-drivers` (in `production`, queue `sync`, cache `array` / `null`, session `array`, mail `log` / `array`: warn, medium, one row per driver), `laravel-log-level` (in `production`, the default log channel logs at `debug`: warn, low) and `laravel-dev-packages` (in `production`, Telescope, Debugbar, Ray, Pail or Clockwork listed in `composer.json` `require` instead of `require-dev` and enabled in the booted app: warn, medium, one row per package). Findings name the config key and the problem, never the value. New `details`: `laravel-cors-wildcard` `hasCredentials`, `laravel-production-drivers` `component`, `driver`, `laravel-dev-packages` `package`, documented in `docs/report-schema.json`. SARIF locations `config/app.php`, `config/session.php`, `config/cors.php`, `config/logging.php` and `composer.json`. Additive: new check ids registered after the existing ones, optional `details`; `schemaVersion` stays `1`.
- Release identifier and deploy markers (#129), all additive (schema and protocol versions stay `1`): an optional `release` on the JSON report and push payload, on runtime batches (`runtime.release`) and on exception batches (`exceptions.release`; the group fingerprint does not change). It is resolved from the new `excubia.json` key `release`, the new environment variable `EXCUBIA_RELEASE`, then `GITHUB_SHA`, `CI_COMMIT_SHA`, `VERCEL_GIT_COMMIT_SHA`, `FORGE_DEPLOY_COMMIT`, `LARAVEL_CLOUD_COMMIT`, and for the standalone CLI the commit in the project's `.git` (read from `HEAD` and the ref file or `packed-refs`, without running `git`). Up to 100 characters of `[A-Za-z0-9._+/@-]`, otherwise `null`. New option `--deploy` on `push` and `excubia:push` adds `deployedAt` to the report so excubia-app can draw a deploy marker; the CI and excubia-app guides show it as the post-deploy step.
- New check `dependency-licenses` (#134), in the standalone CLI and in Artisan: a license inventory of the locked Composer and npm packages, read from the `license` entries of `composer.lock` and `package-lock.json` (lockfileVersion 2 and 3) without any request. A license in `checks.dependency-licenses.denied` fails at high, a strong copyleft license (GPL, AGPL, SSPL, EUPL, OSL, RPL, Sleepycat) warns at medium, a missing or unknown license warns at low; `allowed` licenses never warn. SPDX expressions are read with `OR`, `AND`, parentheses, `WITH` and the `+` / `-only` / `-or-later` suffixes, so `MIT OR GPL-3.0-only` passes. New `excubia.json` keys `checks.dependency-licenses.allowed`, `.denied` (SPDX ids or globs) and `.includeDev` (default `false`). Finding `details`: `package`, `lockedVersion`, `licenses`, `ecosystem`. New optional top-level report field `licenses` with the counts per license id and per ecosystem (`composer`, `npm`). SARIF results point at the package's lockfile. All additive: `schemaVersion` and the schemas' `x-excubia-version` stay `1`; the check id is appended to the run order, so every existing check id keeps its position.
- Seven more runtime aggregate types (#132), each off by default with its own `runtime.<type>.enabled` and `sampleRate` (new `excubia.json` keys `runtime.requestMemory`, `jobMemory`, `queueWait`, `cache`, `mail`, `notifications`, `logLevels`): `requestMemory` (peak MB per route name and method), `jobMemory` (peak MB per job class and queue; the PHP peak is reset when a job starts), `queueWait` (ms between push and first attempt, without the delay, from an `excubiaQueuedAt` timestamp added to job payloads or Horizon's `pushedAt`), `cache` (hits, misses, writes and deletes per store and key prefix cut at the first `:` or `.`, masked, `[masked]` when it still looks like an id or token), `mail` (sent per mailable and mailer; failed only when exception capture sees a reported Symfony Mailer transport exception, since Laravel has no mail failure event), `notification` (sent and failed per class and channel) and `logLevel` (count per level; `MessageLogged` has no channel, and the message and context are never read). New aggregate metric fields `totalMb`, `maxMb`, `hits`, `misses`, `writes`, `deletes`, documented in `docs/runtime-schema.json` with a rule for apps: accept a batch with an unknown type and skip those entries. Additive: the five existing types and their defaults are unchanged; `x-excubia-version` and `protocolVersion` stay `1`. The overhead benchmark now runs with every type on.
- Infrastructure health checks (#131), as in spatie/laravel-health and Oh Dear, run by `php artisan excubia:check` and `excubia:push` and `skipped` ("requires Artisan") in `vendor/bin/excubia`: `laravel-database` (`select 1` on the default connection and on `checks.laravel-database.connections`: fail, critical, one row per connection; a connection opened for the probe gets a 3 s connect timeout and is closed again), `laravel-cache` (write, read and delete a random probe key on the default store: fail, high; skipped with the `null` driver), `laravel-storage` (`storage` or `bootstrap/cache` not writable: fail, high), `laravel-disk-space` (disk holding `storage/` at least 80 % used: warn, medium; at least 90 %: fail, high) and `laravel-queue-backlog` (oldest pending job older than 15 minutes or more than 1000 pending, per queue, `database` and `redis` drivers only: warn, medium). Plus `php-platform-requirements`, which also runs in the standalone CLI: `php` and `ext-*` requirements of the locked packages and the root `platform` that the running PHP does not meet, like `composer check-platform-reqs` (fail, high, one row per requirement; the standalone CLI says it checked its own PHP). Probes catch every error and report no hostname, DSN, credential or absolute path. The health endpoint maps them like every check. New `details`: `laravel-database` `connection`, `laravel-cache` `store`, `laravel-storage` `directory`, `laravel-disk-space` `usedPercent`, `laravel-queue-backlog` `queue`, `pendingCount`, `oldestAgeMinutes`, `php-platform-requirements` `requirement`, `requiredBy`, `checkedPhpVersion`, `isStandaloneCli`. New `excubia.json` keys `checks.laravel-database.connections`, `checks.laravel-disk-space.warnAtPercentUsed` / `failAtPercentUsed`, `checks.laravel-queue-backlog.maxOldestAgeMinutes` / `maxPendingJobs` / `queues`. Additive: new check ids registered after the existing ones, optional `details` and config keys; `schemaVersion` stays `1`.
- New check `env-example-sync` (#13), in the standalone CLI and in Artisan: compares the environment keys that `config/*.php` reads (`env('KEY')`, `\env('KEY')`, `Env::get('KEY')` with a literal key, found with PHP's tokenizer, never executed) with the key names in `.env.example` (`export KEY=` and commented-out `# KEY=` included; values dropped while reading). It never opens `.env` and never reports a value. A key read in `config/` but missing from `.env.example` warns at low, one row per key; keys in `.env.example` that no config file reads are one `info` row (subject `unused keys`). Skipped (`not-applicable`) without `.env.example` or `config/`. New `excubia.json` keys `checks.env-example-sync.ignoreKeys` (key names or globs, added to a documented default list of optional Laravel 12 and 13 keys such as `AWS_*`, `PUSHER_*`, `VITE_*`, `MEMCACHED_*`, `REDIS_CLIENT`) and `checks.env-example-sync.useDefaultIgnoreKeys` (default `true`; `false` replaces the defaults). Finding `details`: `key`, `configFiles` (project-relative), and `keys` on the summary row. SARIF location `.env.example`. All additive: `schemaVersion` and the schemas' `x-excubia-version` stay `1`; the check id is appended to the run order, so every existing check id keeps its position.
- New check `composer-outdated` (#150), in the standalone CLI and in Artisan, like `composer outdated --direct`: each direct dependency of `composer.json` (`require`, plus `require-dev` unless `--no-dev`) is compared with the newest stable Packagist release using `composer/semver`. Behind only on a patch warns at `info`, behind on a minor or a major at `low`, one row per package. Pre-releases count only when the locked version is a pre-release; `minimum-stability` is not read; locked dev branches are left out; private packages get the usual `private packages` row. It reads the same Packagist p2 metadata as `composer-abandoned` and `composer-stale`: `PackagistApiService` now keeps each parsed response for the run, so the metadata is requested once per package even with the response cache bypassed. Finding `details`: `package`, `lockedVersion`, `latestPatch`, `latestMinor`, `latestMajor` (each `null` when nothing newer exists at that level), `isMajorBehind`. The upgrade plan gets one last step, "Update to the latest patch: …", for the outdated packages without a `composer-advisories` finding. SARIF location `composer.lock`. npm direct dependencies are not covered yet. All additive: `schemaVersion` and the schemas' `x-excubia-version` stay `1`; the check id is appended to the run order, so every existing check id keeps its position.
- Opt-in PHP deprecation counts for upgrade readiness (#133): new runtime aggregate type `deprecation`, off by default, switched by the new `excubia.json` key `runtime.deprecations` (`enabled`, `sampleRate`). When the provider boots it chains a PHP error handler in front of Laravel's that counts `E_DEPRECATED` and `E_USER_DEPRECATED` and always calls the previous handler and returns its result (`false` when there is none), so Laravel's `deprecations` log channel, its warning-to-exception conversion and other handlers keep working. Grouped per UTC minute by `source` (`app`, `vendor/<vendor>/<package>` or `unknown`), `message` (exception message masks, at most 300 characters) and `phpVersion` (`8.4`); never the file path, line or stack. A request that raises no deprecation never calls the handler (benchmark delta within noise). The standalone CLI is not affected. Additive: `x-excubia-version` and `protocolVersion` stay `1`.
- Latency histograms for percentiles (#147): the `request`, `slowQuery`, `job`, `scheduledTask`, `outgoingHttp` and `queueWait` runtime aggregates carry a new optional `histogram`, 12 counts per fixed bucket (upper bounds 5, 10, 25, 50, 100, 250, 500, 1000, 2500, 5000 and 10000 ms, inclusive, plus an overflow bucket) that add up to `count`, so excubia-app can show p50, p95 and p99 by linear interpolation inside a bucket (recipe in `$defs.histogram` of `docs/runtime-schema.json`). The buffer and the app merge histograms element by element; a merge where one side has no histogram or a different number of buckets drops it rather than send counts that disagree with `count`. The bounds are a public contract (`docs/CONTRACTS.md`, contract snapshot). About 0.0002 ms per sample in the overhead benchmark. Additive: no new `excubia.json` key, `x-excubia-version` and `protocolVersion` stay `1`.

- Yarn and pnpm lockfiles (#21): `yarn.lock` from Yarn classic (v1) and Yarn Berry (v2+) and `pnpm-lock.yaml` lockfileVersion 6 and 9 feed `npm-advisories`, the private-packages rules and `dependency-licenses` like `package-lock.json`. When several lockfiles exist, the one matching `package.json` `packageManager` is read, else the first of `pnpm-lock.yaml`, `yarn.lock`, `package-lock.json`. A package is private unless it resolved from `registry.npmjs.org` or `registry.yarnpkg.com` (now also for `package-lock.json`); for Yarn Berry and pnpm, scopes or a default registry that `.yarnrc.yml` / `.npmrc` point at another server are private too. Those two files are read for registry URLs only; credentials (`_authToken`, `_auth`, `_password`, `npmAuthToken`, `npmAuthIdent`) are ignored line by line and never kept, sent or reported. Yarn and pnpm record no licenses, so `dependency-licenses` reports those packages in one `skipped` row ("N packages from yarn.lock have no license data") instead of a low warning each. The YAML of Berry and pnpm is read by a small dedicated parser, no new dependency. New optional top-level report field `javascriptLockfile` and `npm-advisories` `details.lockfile`; the SARIF location of npm findings is the lockfile that was read. Additive: `schemaVersion` and the schemas' `x-excubia-version` stay `1`. The `npm-advisories` skip message now names the three lockfiles.

### Fixed

- `check` and `push` with `--fail-on`, `--no-dev` or `--strict` dropped the `runtime`, `exceptions` and `privacy.skipPackages` settings of `excubia.json` for that run, so packages matched by `privacy.skipPackages` could be sent to the public data sources (#129).

## [1.0.0-beta.1] - 2026-11-03

First beta of 1.0. Every 1.0 feature is in, and the public contracts listed in [`docs/CONTRACTS.md`](./docs/CONTRACTS.md) are frozen: until 1.0.0 only backwards-compatible fixes land. Upgrading from 0.x: [`docs/guides/upgrading.md`](./docs/guides/upgrading.md).

### Added

- Contracts frozen for 1.0.0-beta (#76): `docs/CONTRACTS.md` lists every public contract (report JSON, check ids, exit codes, `bin/excubia` and Artisan commands and options, scheduled entries and the heartbeat cache key, `excubia.json` and environment variables, push envelope and endpoints, runtime and exception payloads, health endpoint, SARIF rule ids and fingerprints, GitHub Action inputs and outputs, `skipReason` values) with its source files, version field and contract test; everything else (PHP classes, message wording, table and Markdown layout) is internal. Every schema file now carries `x-excubia-version: 1`, and `tests/Feature/PublicContractsTest.php` plus `tests/Laravel/ScheduleAndRouteContractTest.php` compare the code with the snapshot in `tests/Fixtures/Contracts/public-contracts.json`, so an unannounced contract change fails CI. The `--strict` (#15) and posture checks (#73) decisions are in. No contract changed.

- Structured report fields for excubia-app (#92), all optional so `schemaVersion` stays `1`: top-level `generatedAt` (UTC), `excubiaVersion` (the `--version` value) and `project` (`php`, `laravel`, `node`, each `{version, cycle, securitySupportEndsOn, activeSupportEndsOn}` or `null`; no name, path or hostname). The cycle and support end dates are filled from the endoflife.date responses the EOL checks already fetch, also when they pass, so a healthy project carries its support window (#123); they are `null` when the check was skipped or did not run; per finding `fingerprint` (sha256 of check id, subject and advisory id, the same value as the SARIF `partialFingerprints`), `advisoryId` when present (it was already in the schema but not printed) and `details` with check-specific keys: advisories `package`, `lockedVersion`, `fixedVersions` (plus `affectedVersions` for Composer), EOL checks `cycle`, `securitySupportEndsOn`, `activeSupportEndsOn`, `composer-abandoned` `package`, `lockedVersion`, `replacement`, `composer-stale` `package`, `lockedVersion`, `laravel-next-blocker` `package`, `lockedVersion`, `targetMajor`, `laravel-pending-migrations` `count`, `laravel-failed-jobs` `count`, `oldestAgeHours`, `laravel-scheduler-heartbeat` `minutesSinceLastRun`, and the private packages row `count`. Documented per check id in `docs/report-schema.json`; the push payload carries them. Table, Markdown and SARIF output are unchanged.
- `excubia.json` key `privacy.skipPackages` (#108): a list of package name globs (`*` and `?` only, for example `acme/*` or `@acme/*`) that are never sent to a public data source and are reported as skipped. Documented in `excubia.schema.json` and the configuration guide.
- User documentation for 1.0 (#85): the README is the entry point (quick start, check table, formats, every CLI and Artisan option, exit codes), with guides in `docs/guides/` for configuration (every `excubia.json` key and environment variable), CI, the push to excubia-app, runtime monitoring, exception capture, the health endpoint, privacy and upgrading from 0.x. `tests/Feature/DocumentationCoverageTest.php` fails when a CLI or Artisan option, Artisan command, check id, `excubia.json` key or environment variable is missing from the docs.
- Opt-in exception capture for Laravel apps (#77, D17), off by default and independent of runtime monitoring: `excubia.json` key `exceptions` (`enabled`, `maskPatterns`, `ignore`, `bufferMaxBytes`). When enabled, the provider adds one `reportable()` callback to the exception handler that returns nothing, so the app's own reporting is unchanged; disabled, nothing is registered. Each reported exception is masked before it is written to `storage/excubia/exceptions/` (emails, JWTs, bearer tokens, key=value secrets, API-key-like strings, UUIDs, card-like and long numbers, IP addresses, URL credentials and query strings, quoted SQL literals, database hosts, absolute paths, plus `maskPatterns`), grouped by a sha256 fingerprint of the class and the in-app frames without line numbers, with stack frames as relative file, line and function (no arguments), the chained exception classes, the route, job or command context, the environment, a count and first / last seen. Errors inside the capture never reach the app.
- `php artisan excubia:push-runtime` also sends the exception buffer to `POST {url}/api/exceptions` when `exceptions.enabled` is true (envelope `protocolVersion: 1`, `type: "exceptions"`, payload `docs/exception-schema.json`, referenced from `docs/push-schema.json` `$defs.exceptionsEnvelope`), and is scheduled every minute when either opt-in is on. A failure sending one buffer does not stop the other; the exit code is then `3`.

- Six configuration posture checks, run by `php artisan excubia:check` and `excubia:push` on the booted app (#73): `laravel-debug-mode` (`app.debug` on outside `local` / `testing`: fail, high), `laravel-production-caches` (config, route or event cache missing in `production`: warn, low, one row per cache), `laravel-pending-migrations` (fail, medium), `laravel-failed-jobs` (warn, medium; high once the oldest is 24 hours old), `laravel-scheduler-heartbeat` (no heartbeat for more than 10 minutes: warn, medium) and `laravel-maintenance-mode` (warn, medium). `vendor/bin/excubia` cannot boot the app and reports them as `skipped` ("requires Artisan", `not-applicable`). Findings carry only booleans, counts, ages and names. New check ids, registered after the existing ones; `--only`, `--skip` and ignore rules work as for the other checks.
- `php artisan excubia:heartbeat`, scheduled every minute by the service provider: stores the Unix time under the cache key `excubia:scheduler-heartbeat` for `laravel-scheduler-heartbeat`. It is the only write of the posture checks.
- `excubia.json` keys `checks.laravel-scheduler-heartbeat.staleAfterMinutes` (default `10`) and `checks.laravel-failed-jobs.highSeverityAfterHours` (default `24`), in `excubia.schema.json`.
- SARIF locations for the posture checks: `config/app.php`, `config/queue.php`, `database/migrations` or `routes/console.php`.
- Opt-in runtime monitoring for Laravel apps (#75), off by default: `excubia.json` key `runtime` (`enabled`, `bufferMaxBytes`, and per type `requests`, `slowQueries` with `thresholdMs`, `jobs`, `scheduler`, `outgoingHttp`, each with `enabled` and `sampleRate`). When enabled, the provider listens to `RequestHandled`, `QueryExecuted`, `JobProcessing` / `JobProcessed` / `JobFailed`, `ScheduledTaskFinished` / `ScheduledTaskFailed` / `ScheduledTaskSkipped` and the HTTP client's `ResponseReceived`, aggregates per minute in memory and writes to a size-capped buffer under `storage/excubia/runtime/` (oldest entries dropped first); disabled, no listener is registered. Errors inside the collection never reach the app.
- `php artisan excubia:push-runtime`, scheduled every minute when runtime monitoring is on: sends the buffer to `POST {url}/api/runtime` with the push URL, token and transport. Envelope `protocolVersion: 1`, `type: "runtime"`, `batchId` kept across retries until the app answers 2xx, payload documented in `docs/runtime-schema.json` and referenced from `docs/push-schema.json` (`$defs.runtimeEnvelope`). Exit codes `0` / `2` / `3` as for `push`.
- `--strict` on `check` and `push` (and `excubia:check` / `excubia:push`), also the `excubia.json` key `strict`: a check skipped because a data source failed (network down and no cache, or an API error) makes the command exit `3`, with a message naming each check and data source. `push --strict` then sends nothing. Deliberate skips (`--offline` without cache, `--only` / `--skip`, Laravel checks on a non-Laravel project, ignore rules) never exit `3`. Precedence `2` > `1` > `3`. The flag can only turn strict mode on. Without `--strict` nothing changes.
- Optional finding field `skipReason` in the JSON report (`data-source-failure`, `offline`, `not-applicable`), set on every `skipped` finding and documented in `docs/report-schema.json`. Additive, so `schemaVersion` stays `1`.
- `HealthCheckRunnerService::runForSnapshot()` runs the checks on a `ProjectSnapshotData` built by the caller, without reading a project directory.
- `vendor/bin/excubia push [path]` and `php artisan excubia:push` run the checks and send the report to your own `excubia-app` (`POST {url}/api/reports`, `Authorization: Bearer`). Envelope `protocolVersion: 1` with a unique `batchId` and `sentAt`, documented in `docs/push-schema.json`. Exit codes: `0` sent, `2` configuration error, `3` token rejected or app unreachable.
- `excubia.json` key `app` (`url`, `token`); `EXCUBIA_APP_URL` / `EXCUBIA_APP_TOKEN` override it. HTTPS only, plain HTTP allowed for localhost.
- `--format=sarif` writes a SARIF 2.1.0 log for GitHub code scanning: one rule per check id, one result per `fail` or `warn` finding (`critical`/`high` → `error`, `medium` → `warning`, `low`/`info` → `note`, Excubia severity in `properties.severity`), the manifest as a project-relative location, and `partialFingerprints` that stay stable across runs.
- Composite GitHub Action (`action.yml`, `qiick-io/excubia-core@v1` once tagged): installs Excubia from the action's own checkout in `$RUNNER_TEMP`, outside the scanned project, runs `excubia check --format=sarif`, writes the Markdown report to the job summary and uploads the SARIF log with `github/codeql-action/upload-sarif`. Inputs `path`, `fail-on` (default `critical`), `only`, `skip`, `github-token`, `upload-sarif` (default `true`) and `php-version` (default `8.4`); the step fails according to `fail-on` after the upload. Tested by `.github/workflows/action-test.yml`.
- Opt-in health endpoint in the Oh Dear application health JSON format for Laravel apps (`docs/health-endpoint.md`): `excubia.json` keys `healthEndpoint.enabled` (default `false`) and `healthEndpoint.path` (default `excubia/health`), secret from `EXCUBIA_HEALTH_SECRET` (the route is not registered without it), checked against the `oh-dear-health-check-secret` header with `hash_equals`; a wrong or missing secret gets `404`. The endpoint serves the result the last `excubia:check` / `excubia:push` stored in `storage/excubia/health.json` and never runs checks in the request. `pass` → `ok`, `warn` → `warning`, `fail` → `failed`, `skipped` → `skipped`, a run without a report → one `crashed` entry; no stored result yet → one `skipped` entry.

### Changed

- Supports Symfony 8 (#113): `symfony/console` and `symfony/http-client` now allow `^7.2 || ^8.0`, so `composer require qiick/excubia-core` installs in a Laravel 13 app that already locks Symfony 8 components, without `-W`. Symfony 8 needs PHP 8.4 or newer; on PHP 8.2 and 8.3 Composer keeps Symfony 7. `bin/excubia` registers its commands with `addCommands()`, which both majors provide (`Application::add()` was removed in Symfony 8).

### Removed

- Laravel 11 is no longer supported for the Artisan integration (D19): it is past security support and Composer blocks its releases by default. The standalone CLI still scans Laravel 11 projects and reports them as end of life.

### Fixed

- The upgrade plan no longer repeats near-identical steps: one step per vulnerable package (`fixes N advisories`), one step naming every package that blocks the next Laravel major, one step per abandoned package, one step for all stale packages, and the Laravel end-of-life step no longer repeats "Upgrade to Laravel N". Identical steps are dropped. The `upgradePlan` JSON shape is unchanged; only step messages and count differ.

### Security

- Private package names are no longer sent to Packagist, OSV.dev or GitHub (#108). A Composer package is checked only when its `composer.lock` entry has Packagist's `notification-url` and no `path` or `artifact` dist (path, artifact, VCS, Satis and Private Packagist packages are private); an npm package only when `resolved` is on `https://registry.npmjs.org/` and it is not a link (`file:`, VCS, workspace and other-registry packages are private). `composer-advisories`, `npm-advisories`, `composer-abandoned`, `composer-stale` and `laravel-next-blocker` report them in one `skipped` row with subject `private packages`, `skipReason` `not-applicable` and the skipped names in the message, so such a check can show `skipped` instead of `pass`; the exit code and `--strict` are unchanged.
- Threat model of every outgoing and stored data path: `docs/SECURITY-MODEL.md` (#82). `SECURITY.md` names the supported versions for 1.x.
- The default response cache directory is per user (`<temp>/qiick-excubia-<uid>`) and is skipped when it is a symlink, owned by another user or writable by group or others, so another local user cannot plant responses that hide advisories. `cache:clear` deletes only files named like cache entries.
- `push` and `excubia:push-runtime` no longer follow redirects: a 3xx from the app is an error, so the envelope is never resent to another host or over plain HTTP.
- URL credentials (`https://user:password@…`) are removed from the app URL in error messages and in the `-v` request list.
- Exception masking also covers `'key' => 'value'` dumps, quoted values with spaces, unterminated quotes and the `pass`, `cookie`, `session`, `dsn` and `private_key` key names.
- Scheduled task names in runtime data go through the same masks, so `--password=…` and similar arguments are not buffered or sent.
- Scheduled task names in runtime data (#109) drop every argument: an Artisan command is `artisan <command name>` and an `exec()` task is the executable's file name (leading `VAR=value` assignments skipped), so secrets in forms no mask recognises (`-pSECRET`, positional arguments) are never buffered or sent, and arguments no longer create new aggregates. A task description set by the developer is kept, masked as before. This changes the documented `task` value in `docs/runtime-schema.json` and SPEC §7.
- GitHub owner and repository names `.` and `..` are refused before a request is built.
- The GitHub Action (#111) installs Excubia's dependencies from a committed lock (`.github/action-install/composer.lock`, resolved for PHP 8.2) instead of resolving them on every run, with `--no-plugins --no-scripts`. A test keeps the lock in sync with `composer.json`, and `.github/workflows/action-test.yml` also runs the action on PHP 8.2.
- `check`, `push`, `excubia:check`, `excubia:push` and `excubia:push-runtime` print one warning on stderr when `app.token` is set in `excubia.json` (#110): "app.token is set in excubia.json; prefer EXCUBIA_APP_TOKEN so the token is not committed." The key keeps working; README, the configuration and push guides and `excubia.schema.json` say the same.
- Slow-query SQL in runtime data and the SQL of captured query exceptions (#106) also replace standalone numbers, hex literals (`0x…`, `X'…'`) and dollar-quoted bodies (`$$…$$`, `$tag$…$tag$`) with `?`, not only single-quoted strings. Placeholders (`$1`, `?`), identifiers such as `t1` and double-quoted or backtick-quoted identifiers stay. This changes the documented `sql` value in `docs/runtime-schema.json` and SPEC §7: queries that differed only by an inline value now share one aggregate.
- Exception masking (#104) also replaces URL hosts and ports and host names after `host:`, `hostname=`, `resolve host` and `getaddrinfo for` with `[host]`, reduces Windows drive paths (`C:\…`, `C:/…`) and UNC paths (`\\server\share\…`) to the file name, masks the whole value of an `Authorization` / `Proxy-Authorization` header for any scheme other than `Bearer` / `Basic` (`Token`, `Digest`, `AWS4-HMAC-SHA256`…), and masks phone-like numbers (`+` and 8 or more digits) and US social security numbers as `[number]`. The masked message text of exception groups changes accordingly.
- Health endpoint (#107): `EXCUBIA_HEALTH_SECRET` must be at least 32 characters; a shorter secret counts as no secret, so the route is not registered, and `excubia:check` / `excubia:push` print a warning on stderr. The route is throttled with Laravel's `ThrottleRequests` middleware at 60 requests a minute per client IP (`429` above it).
